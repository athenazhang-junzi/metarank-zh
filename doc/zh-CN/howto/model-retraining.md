## 点击链收集

Metarank 在处理事件时自动收集点击链：

1. 接收 `ranking` 时记录当时用于排序的全部特征值；
2. 在默认 30 分钟窗口内收集与该排序关联的交互；
3. 窗口结束后持久化排序、交互和历史特征值；
4. 将点击链展开为 LambdaMART 使用的隐式判断列表。

动态特征会持续变化，因此必须保存排序发生当时的值，避免训练时使用未来状态。

## 手动重训练

服务使用 Redis 等共享存储时，可以在独立环境运行：

```bash
java -jar metarank.jar train --config /path/to/config.yml
```

训练程序会：

- 从训练存储读取点击链；
- 转换为 XGBoost/LightGBM 判断列表；
- 按配置切分训练集与测试集；
- 训练模型并输出指标和特征权重；
- 把模型上传到状态存储；
- 通知 API 实例重新加载模型。

本地训练配置必须与在线服务的存储连接、特征定义和模型名称一致。不要使用修改后的特征配置去读取旧点击链并默认认为二者兼容。

## 自动重训练

官方 Kubernetes Helm 配置可以创建 CronJob：

```yaml
train:
  enabled: true
  schedule: '"0 6 * * *"'
  resources: {}
```

该示例每天 6:00 训练全部模型。具体时间按照 Kubernetes CronJob 所在环境的时区解释，部署时应显式确认。

模型训练可能需要大量内存和 CPU，应为 CronJob 单独设置资源请求与限制，并避免与高峰推理流量争抢资源。

## 上线前检查

- 新训练数据的时间范围和事件完整性；
- 训练/测试切分是否避免未来泄漏；
- 测试指标是否达到预设门槛；
- 模型大小和推理延迟；
- 特征缺失和分布变化；
- 新模型是否可以回滚；
- 多个服务实例是否成功加载同一版本。

定时训练不等于自动发布。生产环境应在加载前设置质量门禁和回滚机制。
